# FusionGo 系统搭建阻塞问题与复盘记录

> 文档用途：持续记录从项目启动、前后端建设、G-Link/F-Link 接口联调到生产发布期间遇到的阻塞、根因、处理方式和复盘结论。  
> 首次整理：2026-07-30  
> 当前环境：本地前端 + 本地 API + SQLite + FCG Sandbox  
> 维护原则：不记录 App Secret、完整 `priceKey`、旅客证件号等敏感信息；外部原因未得到供应商确认时，不把推测写成事实。

## 1. 当前结论

系统已具备本地酒店、机票搜索、验价/验房、下单、支付、订单查询、取消、客户、定价和财务基础能力；G-Link 酒店真实 Sandbox 主链路已经通过，F-Link 的搜索、验价、创建、支付、查单、取消和改签查询已经通过。

当前仍不能直接面向生产用户开放，主要阻塞是：

1. F-Link 多张已支付测试单长时间处于 `5=出票中`；儿童与往返新订单支付约 50 分钟后复核仍未出票，退票、改签和完整出票验收受影响。
2. G-Link 尚未通过供应商到公网 HTTPS 地址的真实 Webhook 推送验收。
3. 尚未取得并验证 G-Link/F-Link `production_active` 凭证。
4. 生产身份认证、真实支付/授信对账、PostgreSQL/Redis、消息队列、监控告警和备份恢复尚未落地。
5. 当前项目目录未检测到 Git 仓库，缺少正式的版本基线、变更追踪和发布回滚记录。

## 3. 高影响事件复盘

### 3.1 模拟酒店订单被误认为真实上游下单

**现象**

页面可以完成酒店搜索、验房、创建、支付和订单详情，但用户核对后发现并未真实调用 G-Link 创建订单。

**根因**

初期为了先验证 UI 和本地订单状态机，在 G-Link 无可售测试资源时启用了本地模拟房态。模拟链路有提示，但“页面能走通”仍容易被误解为“供应商接口已验收”。

**处理**

1. 把真实与模拟库存分开标记。
2. 增加 `FCG_SANDBOX_HOTEL_SIMULATION` 显式开关。
3. 真实 Sandbox 默认关闭模拟；生产环境永久禁止模拟。
4. 只有完成可售目录、最低价、实时产品、两次验房后，才允许调用真实创建订单。
5. 使用真实测试产品完成 G-Link 创建、支付、查单和取消验收。

**复盘结论**

页面流程通过、Mock 通过、Sandbox 真实下单通过、生产小流量通过必须是四个独立验收结论，报告中不得合并表述。

### 3.2 F-Link 金额不一致

**现象**

支付页显示票价加行李、选座和保障共 CNY 1,269，但订单、支付记录和数据库只有供应商票款 CNY 861。

**根因**

前端计算了本地增值服务，后端只使用供应商返回金额创建本地订单。

**处理**

- 保存 `supplierAmount`、`addOnAmount` 和客户最终售价。
- 供应商支付只使用供应商应付金额。
- 客户支付、授信扣减和财务流水使用客户最终售价。
- 增加前后端金额一致性回归。

**复盘结论**

供应商成本、平台加价、本地增值服务、税费、客户应付必须在数据模型中分列，不能只保存一个 `amount`。

### 3.3 F-Link 状态误映射

**现象**

订单页面先显示已出票，刷新供应商状态后变为已取消。

**根因**

早期状态码映射没有严格按当前 Swagger 的 1–9 枚举实现，同时本地终态缺少冲突保护。

**处理**

- `5` 映射为出票处理中，`8` 才映射为已出票，`9` 映射为取消。
- 持久化原始状态码和每次同步事件。
- 已出票、已确认、已取消等终态发生逆向变化时记录冲突，不静默覆盖。

**复盘结论**

供应商状态不能直接作为本地状态；必须建立稳定的本地状态机、原始状态审计和非法跃迁保护。

### 3.4 F-Link 退改被异步出票阻塞

**现象**

SIN→BKK 搜索、验价、创建、支付均成功，但两张订单持续为 `5=出票中`：

- 改签查询可以返回报价，改签申请返回“未查询到订单信息”。
- 退票申请返回“订单未完成，无法退票”。

**已产生的测试订单**

| 用途 | 本地订单 | F-Link 订单 | 当前状态 |
| --- | --- | --- | --- |
| 改签 | `FG20260730000003` | `dd20260730155607647185074` | `5=出票中` |
| 退票 | `FG20260730000005` | `dd20260730160307655840270` | `5=出票中` |
| 取消 | `FG20260730000004` | `dd20260730155612324758390` | 已取消 |
| 持续下单回归 | `FG20260730000006` | `dd20260730162516777070529` | 支付成功，`5=出票中` |

**处理原则**

- 不在出票中状态伪造退改成功。
- 改签/退票失败后确认未生成售后单，避免遗留副作用。
- 两张订单分别保留给改签和退票，避免同一订单完成一项售后后无法测试另一项。

**后续**

供应商将订单更新为 `8=出票成功` 后：

1. 改签单执行 `change.search → change.apply → type=1 支付（如需）→ change.detail`。
2. 退票单执行 `refund.apply → refund.detail → refund.confirm`。

### 3.5 密钥在截图中可见

**现象**

配置 `.env` 时，本地截图中出现过明文沙箱 App Key/App Secret。

**风险**

即使截图只在本地或当前任务中使用，也不应继续把这组密钥当作长期可信凭证。

**处理与要求**

- 文档、测试输出、状态接口和日志不得回显密钥。
- `.env`、SQLite、日志和构建产物不进入版本库或镜像。
- 当前 Sandbox 联调结束后轮换相关密钥。
- 生产使用全新 `production_active` 凭证，并保存到部署平台 Secret/KMS。

## 4. 前端专项复盘

首轮完整交互测试共 72 项，其中 46 项通过、23 项失败、3 项风险。主要问题不是视觉样式，而是“可见控件没有实际行为”和“视觉选中态与真实状态分离”。

已处理的典型问题：

- 酒店搜索无响应、修改输入后旧错误不消失。
- 房间/旅客选择、酒店筛选、地图、排序和房型标签无行为。
- 支付方式 radio 已切换但卡片高亮未同步。
- 机票低价日期、筛选、排序和票价方案没有驱动真实数据。
- 搜索结果一次渲染 180 张卡片，改为每页 20 条。
- 移动端支付摘要排在表单之前，已调整为先填写信息再支付。
- 下载确认单、电子收据和电子客票按钮无反馈，已补齐或按状态明确禁用。

后续规范：

1. 所有看起来可点击的控件必须有行为、禁用态或“暂未开放”说明。
2. 外层高亮、价格、权益和 CTA 必须由同一个受控状态派生。
3. 每个新页面至少验证桌面、390px 移动端、键盘焦点、加载、错误、空状态和禁用状态。
4. 浏览器截图只能证明可见布局，不能代替屏幕阅读器和完整 WCAG 扫描。

## 5. 接口联调专项复盘

### G-Link

最终真实 Sandbox 主链路：

```text
hotelIdList
→ destination / hotelList
→ lowestPrice
→ productDetails
→ availabilityCheck
→ 二次 availabilityCheck
→ 本地订单落库
→ createOrder
→ payOrder
→ Webhook / orderDetail
→ cancelOrder
```

关键经验：

- 静态酒店存在不等于 Partner 可售。
- 最低价只用于列表参考，详情和成交必须实时查产品并两次验房。
- 支付成功不等于订单确认。
- HTTP 200 不等于业务成功。
- 取消成功后停止轮询；结果未知时不能擅自把本地订单改成已取消。

### F-Link

最终已通过的真实 Sandbox 链路：

```text
flight.search
→ flight.cabin（价格变化时）
→ flight.verify
→ 本地订单落库
→ flight.order.create
→ flight.order.pay(type=0)
→ flight.order.detail
→ flight.order.cancel
```

关键经验：

- 必须保存原始 `priceKey`，发生变价时使用 cabin 返回的新 key。
- 必须保存 `orderNo`，退票和改签都依赖该桥接标识。
- 搜索成功、验价成功、支付成功、出票成功是四个不同状态。
- 退票和改签是独立异步订单，需要独立状态机、金额和人工审核兜底。
