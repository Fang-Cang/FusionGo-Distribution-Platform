# 分销系统建设总蓝图

## 1. 建设目标

建设一个面向 OTA、旅行社、TMC 或企业客户的 B2B/B2C 分销系统，通过 FCG 开放平台获取酒店与机票资源，并完成展示、报价、下单、支付、履约、退改、结算和售后。

一期建议先完成“酒店最小可售闭环”，再扩展机票。酒店业务的旅客、运价、出票和退改复杂度相对低，更适合作为接入底座的首个验证场景。

## 2. 必须先确定的业务决策

| 决策 | 需要明确的内容 |
|---|---|
| 客户类型 | B2B 分销商、企业客户、B2C 旅客，或多租户组合 |
| 销售渠道 | Web、H5、小程序、企业差旅门户、对下游 API |
| 产品范围 | 酒店、机票；国内、国际；现付、预付、授信 |
| 定价方式 | 固定加价、百分比加价、阶梯价、客户协议价、促销 |
| 支付方式 | 在线支付、余额、授信月结、线下收款 |
| 结算方式 | 预存、单结、周结、月结；账单币种与汇率来源 |
| 售后责任 | 自动取消/退改、人工审核、平台工单、客服 SLA |
| 合规边界 | 个人信息、证件、支付、发票、数据留存和跨境传输 |

## 3. 系统范围

### 3.1 用户端

- 注册、登录、企业认证、成员与权限。
- 酒店搜索、筛选、详情、房型与取消政策、验价、预订、支付、订单与取消。
- 机票搜索、航班筛选、运价规则、验价、乘机人、下单、支付、出票、退票与改签。
- 常用旅客、联系人、发票抬头、消息通知和售后工单。

### 3.2 运营后台

- 客户、租户、账号、角色和权限管理。
- 供应商应用与环境配置，密钥仅进入密钥管理服务。
- 产品开关、渠道政策、加价规则、币种与汇率。
- 订单、支付、退款、退改、人工单和异常单处理。
- 余额、授信、账单、对账、结算、发票与财务导出。
- 工单、公告、消息模板、操作审计和数据报表。

### 3.3 对下游开放能力（如需要）

- 为下游客户签发独立凭证。
- 统一酒店/机票产品模型，屏蔽上游差异。
- 限流、配额、签名、防重放、IP 白名单和回调重试。
- 沙箱、API 文档、调用日志、错误码和联调工具。

## 4. 推荐技术架构

```text
Web / H5 / 小程序 / 下游 API
             |
         API Gateway
             |
  身份权限 / 客户 / 产品搜索 / 报价
  订单 / 支付 / 售后 / 结算 / 通知
             |
       FCG Adapter Layer
  签名 / 加解密 / 重试 / 限流 / 映射
             |
       FCG Open Platform
```

基础设施至少包括：

- 关系数据库：订单、客户、资金和配置主数据。
- Redis：会话、热点缓存、分布式锁、幂等键和限流。
- 消息队列：订单状态同步、回调、支付、通知和对账任务。
- 对象存储：账单、发票、导出文件和审计附件。
- 密钥管理：AppSecret、AES Key、支付密钥分环境保管。
- 可观测性：日志、指标、链路追踪、告警和业务看板。

## 5. FCG 接入底座

当前开放平台协议（以 2026-04-24 OpenAPI 和官方 Skills 为准）：

- 网关地址：`https://open.fusionconnectgroup.com`。
- 请求头：`X-OP-App-Key`、`X-OP-Timestamp`、`X-OP-Nonce`、`X-OP-Sign`。
- 签名原文依次为大写 HTTP 方法、实际公共路径、排序查询串、原始请求体 SHA256、时间戳、nonce、App Key，各段使用换行符连接。
- 使用 `open_app_secret` 对签名原文执行 HMAC-SHA256，输出小写十六进制。
- G-Link 实际路径前缀为 `/openapi/v1/glink`；F-Link 为 `/openapi/v1/flink/{lang}`。
- 平台统一返回 `{ request_id, trace_id, downstream_request_id, code, message, data }`。
- 必须同时判断 HTTP 状态和业务字段 `code`；HTTP 200 下的 `SUPPLIER_BIZ_ERROR` 仍属于失败。
- 当前 G-Link/F-Link 公共契约不使用旧版 `X-App-Id` 或 AES 响应解密流程，两套鉴权不得混用。

接入层必须实现：

- 环境和凭证配置、凭证轮换。
- 确定性 JSON 序列化，保证请求体哈希与实际发送正文完全一致。
- 毫秒时间戳、全局唯一 nonce 和时钟偏差监控。
- 统一响应信封解析、类型转换和平台错误映射。
- 超时、熔断、限流和有边界的重试策略。
- 请求关联 ID、脱敏日志、调用指标和审计记录。
- 查询缓存、下单幂等、状态机和异步状态同步。

## 6. 核心交易流程

### 6.1 酒店

目的地/酒店搜索 → 房型与价格展示 → 预订前验价 → 创建本地订单 → 上游预订 → 支付/授信处理 → 确认 → 订单同步 → 取消/退款 → 对账结算。

关键控制点：

- 搜索结果不能直接作为最终成交价，必须在下单前重新验价。
- 取消政策、税费、币种、入住人规则必须保存成交快照。
- 创建订单必须有业务幂等号，避免超时重试造成重复预订。
- 上游超时不等于失败，应进入“结果未知”状态并主动查单。

### 6.2 机票

航班搜索 → 运价展示 → 运价校验 → 乘机人校验 → 创建本地订单 → 占座/下单 → 支付 → 出票 → 票号同步 → 退票/改签 → 对账结算。

关键控制点：

- 搜索、验价、占座、出票是不同状态，不得合并为一次成功。
- 保存航段、舱位、行李、退改规则、乘机人和证件成交快照。
- 出票、退票和改签通常是异步流程，需要任务与人工兜底。
- 严格保护证件号、生日、联系方式等个人敏感信息。

## 7. 订单状态与一致性

本地订单不能直接照搬上游状态码，应建立自己的稳定状态机，再映射 FCG 状态。

建议公共状态：

- `DRAFT`
- `PENDING_PRICE_CONFIRMATION`
- `PENDING_SUBMISSION`
- `SUBMITTING`
- `PENDING_PAYMENT`
- `PROCESSING`
- `CONFIRMED` / `TICKETED`
- `CANCELLING` / `REFUNDING` / `CHANGING`
- `CANCELLED` / `REFUNDED` / `CHANGED`
- `UNKNOWN`
- `FAILED`

所有资金、库存和状态变更必须具备幂等键、版本号或分布式锁，并记录完整状态变更历史。

## 8. 安全与合规

- 密钥不写入源码、数据库明文字段、日志或前端。
- 所有环境独立凭证，生产权限遵循最小授权。
- 个人信息字段加密存储，展示和日志默认脱敏。
- 管理后台启用 MFA、细粒度 RBAC 和高风险操作二次确认。
- 支付回调验签，金额和币种以服务端订单为准。
- 建立数据留存、删除、备份恢复和安全事件响应制度。
- 上线前完成渗透测试、依赖扫描、权限审计和灾备演练。

## 9. 测试体系

- 单元测试：签名、AES-GCM 解密、序列化、状态映射、金额计算。
- 契约测试：按 OpenAPI 验证请求和响应模型。
- Mock 测试：正常、无库存、变价、重复请求、超时、密文损坏和平台错误。
- 沙箱端到端：搜索至取消/退改的完整闭环。
- 财务测试：支付成功但回调丢失、重复退款、差额和跨日对账。
- 性能测试：搜索并发、缓存命中、限流、订单峰值。
- 灾难测试：上游不可用、消息积压、数据库主从切换和恢复。

## 10. 分阶段交付

### 阶段 0：准入与方案

- 完整 API/SDK、沙箱凭证、回调白名单和商务规则到位。
- 产品范围、租户模式、支付结算和一期验收标准确认。
- 数据模型、接口映射、状态机和安全方案评审完成。

### 阶段 1：技术底座

- 工程、环境、CI/CD、数据库、缓存和消息队列。
- FCG Client：签名、解密、错误、超时、重试、日志和 Mock。
- 身份权限、租户、审计、配置与密钥管理。

### 阶段 2：酒店 MVP

- 搜索、详情、验价、预订、订单、支付或授信、取消。
- 运营订单台、异常单、基础加价和基础对账。
- 沙箱全链路验收。

### 阶段 3：机票 MVP

- 搜索、验价、下单、支付、出票、订单。
- 退票、改签申请、异步处理和人工兜底。

### 阶段 4：商业化

- 多租户、客户级定价、余额授信、账单发票。
- 下游 API、配额限流、开发者中心和 SLA。
- 监控告警、安全验收、灰度和生产切流。

## 11. 上线验收门槛

- 酒店和机票各自的核心链路在沙箱通过。
- 重复下单、超时查单、回调重放和退款异常均有验证记录。
- 资金账、业务账、上游账可以自动核对并定位差异。
- 关键接口具备可用性、延迟、错误率和业务成功率告警。
- 生产密钥、域名、证书、白名单、限流和回滚方案就绪。
- 客服、运营和财务有操作手册及异常升级路径。
